## 结论

可以。爬虫和原来的出图用的是同一套模式：节点声明输入输出，画布只负责连线，点运行后从终点节点往回执行，终点节点把结果落到磁盘。

把「加载模型 / 采样 / 保存图片」换成「种子地址 / 请求页面 / 抽取字段 / 保存文件」即可。画布和 prompt 协议不用改。后端继续用现在的 Go 服务，在上面加爬虫节点和执行规则。

一条能落地的图：

```text
SeedURL ──url──► Fetch ──html──► Extract ──text──► SaveText
                    │
                    └──status──► Show
```

`SaveText` 标成终点节点。运行之后，正文写到 `output/`，状态从 Fetch 的第二个输出口进 Show。

## Go 后端的问题

协议层已经能跑通：`/object_info`、`/prompt`、`/ws`、终点节点、中断。缺口在执行器，不在画布。

1. **多个输出口现在是坏的。** `main.go` 里链接的槽位不是 `0` 就直接拒绝。Fetch 要同时给出正文和状态码，第二条线接不出去。做爬虫节点之前先改掉。
2. **一页会抽出很多链接。** 现在每个口只传一个字符串。若为每个链接在画布上生成一个节点，图会炸开，也不是用户拖出来的那张图。列表留在连线的值里，类型用 `URL_LIST`。吃列表的节点在函数内部逐个处理，画布上仍然是一个节点。
3. **爬虫的「再跟进去」是循环，画布上的线必须是有向无环图。** 原先后端发现环会拒绝运行。深度、已访问地址、翻页都放进一个节点的参数里，例如 Fetch 上的 `depth`，或者一个 Frontier 节点：输入是链接列表和深度，输出是页面列表。线不要从后面的节点接回前面的节点。
4. **中断必须取消正在发出的 HTTP。** 现在点中断只会取消任务的 context。节点函数如果不用这个 context 发请求，请求会继续跑完。Fetch 的客户端要用这次运行的 context，并设置超时。
5. **并发要有上限。** Go 适合同时发很多请求。同一张图里可以并行请求彼此无关的地址，但要有共享的运行参数：同时请求数、间隔、单主机上限。没有这些限制，一张列表会把目标站打满。
6. **不要把整页 HTML 从 WebSocket 推回画布。** `executed` 只带摘要：状态码、最终地址、字节数、标题、文件路径。正文留在这次运行的内存里交给下一个节点；太大就先落盘，下一个节点读路径。
7. **同一次运行内去重，运行结束就丢掉。** 已访问集合、Cookie 放在这次 prompt 的上下文里。不要做成进程级全局变量，否则下一次运行会接着上次的状态。
8. **请求节点默认不走缓存。** 原版会在输入没变时跳过节点。对 HTTP 来说，同样的地址两次运行就应该再请求一次。缓存要用户显式打开。
9. **本地服务按用户填写的地址去请求，默认只允许公网 http/https。** 拒绝 `file`、`localhost`、链路本地地址和云元数据地址。访问用户自己的内网需要单独打开一个开关。这是这个工具的默认边界。
10. **单文件会装不下。** 协议可以继续留在 `main.go`。爬虫节点和 HTTP 客户端独立成文件，避免把执行器和选择器写进同一个文件。

原版里最难的一块是运行中再改图（一个节点动态长出许多子节点）。爬虫第一版不做这个。列表在节点内部消化。

## 方案

节点都登记在 Go 里，分类用 `crawl`。前端只看到 `/object_info` 里的新类型，连线规则和现在一样：类型相同才能连。

| 节点 | 输入 | 输出 | 作用 |
|---|---|---|---|
| `SeedURL` | 地址字符串 | `URL` | 源头 |
| `Fetch` | `URL`，超时，深度 | `HTML`、`INT` 状态码、`URL` 最终地址 | 请求。深度大于 1 时在节点内部跟链接 |
| `ExtractText` | `HTML`，CSS 选择器 | `STRING` | 抽出文本 |
| `ExtractLinks` | `HTML` | `URL_LIST` | 抽出链接 |
| `FetchEach` | `URL_LIST`，并发，间隔 | `URL_LIST` 的页面摘要 | 按上限逐个请求 |
| `SaveText` | `STRING` 或 `URL_LIST`，文件名前缀 | 原样往下传 | 终点节点，写入 `output/` |
| `Show` | 任意已有类型 | 无，或原样 | 终点节点，只在节点上显示摘要 |

第一张验收图用 `SeedURL → Fetch → ExtractText → SaveText`，外加 Fetch 的状态码接 `Show`。这条图会强迫执行器支持第 0 个以外的输出口，并真正把文件写到磁盘。

列表、深度和并发放在第二张图：`SeedURL → Fetch → ExtractLinks → FetchEach → SaveText`。

运行时每张图一个 context：取消、超时、并发上限、已访问集合。节点函数签名带上这个 context。WebSocket 仍然按节点发 `executing` / `executed` / `execution_success`。`SaveText` 的 `executed` 里带文件名，和原来保存节点把文件名交回画布的方式一样。

## 实施顺序

1. 执行器接受任意输出槽位。用现有的 `DrawText` 做出两个输出口，确认第二条线能接到下一个节点。
2. 加上面的单页四节点，跑通「请求一个地址，抽出文本，写到 `output/`」。中断能停掉还没返回的请求。
3. 加上 `URL_LIST`、`ExtractLinks`、`FetchEach`，带并发上限和同一运行内去重。
4. 默认拒绝非公网地址。需要访问内网时再加开关。
5. 节点从 `main.go` 拆出去。协议和队列留在原文件。
