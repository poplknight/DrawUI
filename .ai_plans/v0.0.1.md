## 结论

可以。爬虫和原来的出图用的是同一套节点：声明输入输出，画布负责连线。产品是流式的可视化流程，爬虫是其中一条，图像和视频生成不在这里。

现在的 Go 执行器每个节点只跑一次。爬虫要的是另一套：一根线是一条通道，上游没有东西了才停。画布和 `/prompt` 的形状可以保持。后端继续用现在的 Go 服务，换掉 `runPrompt` 里「排好序、调用一次」的循环。

一条能落地的图：

```text
SeedURL ──url──► Fetch ──html──► Extract ──text──► SaveText
                    │
                    └──status──► Show
```

`SaveText` 标成终点节点。运行之后，正文写到 `output/`，状态从 Fetch 的第二个输出口进 Show。

## 执行模型

原版执行器在 `execution.py` 的 `PromptExecutor`。Go 里现在有一版小的，是 `main.go` 的 `runPrompt` 和 `executionOrder`：从没有下游的节点往回收集，排成一个顺序，每个节点调用一次，得到一个值交给下游。Python 里的缓存、子图、异步节点没有搬过来。

要改成和 Go 的 channel 一样。每一根线是一条通道。节点读自己的入口，往自己的出口送东西。

- 来源节点自己生产。种子地址或数据库查出一批 URL，就一条一条送出去，送完把通道关掉。
- 中间节点从入口取值。取到一条就做一条，做出结果再送出去。入口关掉、手里也没有正在做的，它就退出，并关掉自己的出口。
- 工人池是同一个入口上有多个人在读。有空人就领一条；人都在忙，后来的停在通道里。
- 排队节点是只有一个人在读，做完再领下一条。
- 整次运行结束的条件是每条通道都已关闭，每个节点都已退出。

画布上还是一根线。节点声明自己是送出很多条、处理一条出一条，以及同时几个工人。取消运行时，把还在通道里和工人手里的一起停掉。

缺的是执行器里的通道，不是再加一个迭代器节点。迭代器只是通道接上之后可以写的一种节点。整张图也不做成一个大状态机。列表进、列表出的节点以后可以有，重复调用下游的是执行器。

环会把通道堵死。深度、已访问地址、翻页放在节点参数里，或放在这一次运行的上下文里。线保持有向无环。

双击打开 SQLite 管理界面不走这条通道。那是这个节点自己的面板，用单独的查询接口看表、执行 SQL。

## 走到哪

前端已经会画正在执行的节点。WebSocket 的 `progress_state` 里，某个节点的 `state` 是 `running` 时，Nodes 2.0 给它加一圈主题色边框，经典画布给它加一圈绿边。改成 `finished` 之后边框消失。原版执行器在每个节点开始前发这条消息。

Go 现在发的是 `executing` 和 `executed`。前端用它们记下这个节点的结果，描边不看这两条。要看见从 A 走到 E，Go 在调用某个节点之前发 `progress_state`，把这个节点标成 `running`，跑完再标成 `finished`。

现在的 Text、Number、Join、Show 都是立刻返回。五条消息会挤在同一帧里，边框一闪而过。节点自己要花时间，或者执行器在每个节点上停一下让画面画出来，才能看清走动。

通道跑起来之后，消息还要能表示「这条送出去了、还排着几条」。多个节点可以同时处于 `running`，工人池用得上。

## Go 后端的问题

协议层已经能跑通：`/object_info`、`/prompt`、`/ws`、终点节点、中断。缺口在执行器，不在画布。

1. **多个输出口现在是坏的。** `main.go` 里链接的槽位不是 `0` 就直接拒绝。Fetch 要同时给出正文和状态码，第二条线接不出去。做爬虫节点之前先改掉。
2. **一条上游会送出很多条。** 现在每个节点只交出一个值，下游也只跑一次。抽出的链接留在这一根线的通道里，一条一条送给下一个节点。不要为每个链接在画布上生成一个节点。
3. **爬虫的「再跟进去」是循环，画布上的线必须是有向无环图。** 深度、已访问地址、翻页放进节点参数或这一次运行的上下文。线不要从后面的节点接回前面的节点。
4. **中断必须取消正在发出的 HTTP。** 现在点中断只会取消任务的 context。节点函数如果不用这个 context 发请求，请求会继续跑完。Fetch 的客户端要用这次运行的 context，并设置超时。通道里还没被领走的也要停。
5. **并发要有上限。** 工人池的人数、间隔、单主机上限是运行参数。没有这些限制，一张列表会把目标站打满。
6. **不要把整页 HTML 从 WebSocket 推回画布。** 推回的是摘要：状态码、最终地址、字节数、标题、文件路径。正文留在这次运行的通道里交给下一个节点；太大就先落盘，下一个节点读路径。
7. **同一次运行内去重，运行结束就丢掉。** 已访问集合、Cookie 放在这次 prompt 的上下文里。不要做成进程级全局变量，否则下一次运行会接着上次的状态。
8. **请求节点默认不走缓存。** 原版会在输入没变时跳过节点。对 HTTP 来说，同样的地址两次运行就应该再请求一次。缓存要用户显式打开。
9. **本地服务按用户填写的地址去请求，默认只允许公网 http/https。** 拒绝 `file`、`localhost`、链路本地地址和云元数据地址。访问用户自己的内网需要单独打开一个开关。这是这个工具的默认边界。
10. **单文件会装不下。** 协议可以继续留在 `main.go`。通道执行器、爬虫节点和 HTTP 客户端独立成文件。

原版里最难的一块是运行中再改图（一个节点动态长出许多子节点）。爬虫第一版不做这个。多出来的链接走通道，不走新的画布节点。

## 方案

节点都登记在 Go 里，分类用 `crawl`。前端只看到 `/object_info` 里的新类型，连线规则和现在一样：类型相同才能连。分组和标签用节点上的 `group`、`tags`，没有就落在「其他」。

| 节点 | 输入 | 输出 | 作用 |
|---|---|---|---|
| `SeedURL` | 地址字符串 | `URL` 通道 | 源头。可以送出多条，送完关闭 |
| `Fetch` | `URL`，超时，同时几个人 | `HTML`、`INT` 状态码、`URL` 最终地址 | 每取到一条地址就请求一次。人数大于 1 就是工人池 |
| `ExtractText` | `HTML`，CSS 选择器 | `STRING` | 抽出文本，一条进一条出 |
| `ExtractLinks` | `HTML` | `URL` 通道 | 把一页上的链接逐条送出 |
| `Queue` | 任意一条通道 | 同一条通道 | 同时只处理一条，做完再领下一条 |
| `SaveText` | `STRING`，文件名前缀 | 原样往下传 | 终点节点，写入 `output/`。每条都写 |
| `Show` | 任意已有类型 | 无，或原样 | 终点节点，只在节点上显示摘要 |

第一张验收图用 `SeedURL → Fetch → ExtractText → SaveText`，外加 Fetch 的状态码接 `Show`。这条图会强迫执行器支持第 0 个以外的输出口，并真正把文件写到磁盘。人数先设为 1。

第二条图用通道把链接展开：`SeedURL → Fetch → ExtractLinks → Fetch → Queue → SaveText`。第二个 Fetch 的人数大于 1，Queue 保证保存一次只写一条。

运行时每张图一个 context：取消、超时、并发上限、已访问集合。节点函数签名带上这个 context。节点开始和结束发 `progress_state`。`executed` 只带这一条的摘要。`SaveText` 的摘要里带文件名。

## 实施顺序

1. 执行器接受任意输出槽位。用现有的 `DrawText` 做出两个输出口，确认第二条线能接到下一个节点。
2. 把 `runPrompt` 改成按连线建通道。一个来源送出多条，下游每条跑一次，上游关闭后下游退出。同时发出 `progress_state`，五个节点依次亮起能看出来。
3. 加上面的单页四节点，跑通「请求一个地址，抽出文本，写到 `output/`」。中断能停掉还没返回的请求。
4. 加上 `ExtractLinks`、带人数的 `Fetch` 和 `Queue`。同一运行内去重。
5. 默认拒绝非公网地址。需要访问内网时再加开关。
6. 通道执行器和爬虫节点从 `main.go` 拆出去。协议和队列留在原文件。
